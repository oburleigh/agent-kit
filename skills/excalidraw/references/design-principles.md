# Design Principles

These rules apply to every Excalidraw diagram generated by this skill. Read the whole file before placing a single element.

---

## The diagram should argue, not display

A good architecture diagram makes a claim about the system. It is not a furniture plan that enumerates components. It is an argument about how the system is structured and why. Before placing a single node, answer these two questions:

**1. What is this diagram's argument?**
Not "here are our services" but "the system is split along these seams because [reason]". If the argument doesn't fit in one sentence, the diagram is doing too much work.

**2. Is this conceptual or technical?**
Conceptual diagrams explain a pattern to a new reader. Technical diagrams are documentation the team uses to reason about production. The distinction changes every other decision:

| | Conceptual | Technical |
|---|---|---|
| Labels | Role-based ("Auth service") | Concrete ("POST /auth/verify, p99 220ms") |
| Scope | Simplify to the essential nodes | Include everything that matters to operations |
| Evidence artifacts | None needed | Real event names, real endpoints, real payload shapes, code snippets |
| Audience | Someone learning the system | Someone on-call at 3 am |

If the request does not tell you which kind, ask the user.

### The isomorphism test

Before declaring a diagram done: if you removed every text label, would the layout still communicate the central claim? If yes, the shapes are doing the work and the text is reinforcing. If no, the diagram is leaning on labels to make up for missing structural clarity. Restructure the layout so shape, position, and arrows carry the argument. Text adds detail, not the core meaning.

### Evidence artifacts (technical diagrams only)

For technical diagrams, prefer concrete specimens over generic labels:
- An arrow labelled `POST /orders {"items":[{sku,qty}]}` beats one labelled `create order`.
- A queue labelled `kafka: orders.v2` beats one labelled `message queue`.
- A node representing an LLM call labelled `gpt-4o, ~4k input, 800 output` beats one labelled `LLM`.

Code-snippet elements (when they add real value, not clutter) use this colour pair:
- `backgroundColor: "#1e293b"` (dark slate)
- `strokeColor: "#22c55e"` (green text)
- Font family `3` (monospace). This is the ONE place monospace is correct; everywhere else use Helvetica.

## Spacing

All positioning snaps to a 50px grid. Never place elements at arbitrary coordinates. The grid discipline is what makes diagrams feel intentional rather than approximate.

Leave 100px of clear space between unrelated elements. Within a logical group - services in the same bounded context, steps in the same pipeline - 50px is enough. Going below 50px makes the diagram feel cramped even when the labels are short.

Sequence diagrams have their own spacing contract. Participants sit 200px apart horizontally. That gap accommodates the widest activation rectangle plus label without labels from adjacent lifelines colliding. Messages stack 50-80px apart vertically. Use 50px when messages are short and numerous; 80px when each message carries a multi-word label that needs breathing room.

Mind-map hierarchies follow a node-size cascade:

- Centre node: 180 x 100px
- Level 1 branches: 140 x 70px
- Level 2 branches: 100 x 50px
- Level 3 leaves: 80 x 40px

The shrinking sizes reinforce hierarchy visually without needing colour or font tricks. If content doesn't fit a level-3 leaf, promote it to level 2 rather than expanding the leaf.

For non-mind-map layouts, a practical starting canvas is 1400 x 900px. Most diagrams fit within that boundary. If the diagram exceeds it, reconsider scope rather than scaling everything down to compensate. A diagram that requires a 2400px canvas to be readable at normal zoom is usually two diagrams.

## Colour

### The 60-30-10 rule

Sixty percent of the diagram's visual weight should be neutral - white canvas, light fills, transparent frames. Thirty percent goes to the primary accent colour (the dominant service type or the main flow path). Ten percent goes to a secondary accent that draws attention to the most critical element: the decision point, the error path, the external boundary.

Worked example for a microservices diagram: the canvas and frame backgrounds are white (60%). API gateway and internal services use blue fills (#a5d8ff with #1971c2 stroke) throughout (30%). The single external payment provider uses grey (#dee2e6 / #868e96) and the one dead-letter queue uses orange (#ffd8a8 / #e8590c) together (10%).

Breaking this ratio - say, four distinct accent families in a six-service diagram - produces visual noise that makes the reader work to find the important path.

### Semantic colour map

Each semantic role (service, datastore, queue, external, ui, decision, error, ai, evidence, frame, text) gets a stable name. The hex values come from `theme.json` at the skill root, not from this file. The role names are stable across themes; the hex pairs are not. See `references/theming.md` for every key explained and three drop-in palette examples.

Use the role names consistently across diagrams so readers build a visual vocabulary across sessions:

- `service`: microservice, API, function
- `datastore`: database, cache, blob storage, file system
- `queue`: message broker, topic, SQS, Kafka stream
- `external`: third-party API, payment gateway, identity provider
- `ui`: UI component or success state
- `decision`: conditional / branch point (diamond)
- `error`: failure node, circuit breaker, alert
- `ai`: language model, embedding model, inference node (distinct from datastore purple)
- `evidence`: inline code snippets or payload shapes in technical diagrams (always paired with `fontFamily: 3` monospace; counts as content, not structural colour)

### Applying colours in JSON

The layout script reads `theme.colors[<role>].stroke` / `.fill` for every node and emits the values directly. When hand-emitting JSON, mirror the same lookup:

```json
{
  "strokeColor": "<theme.colors.service.stroke>",
  "backgroundColor": "<theme.colors.service.fill>",
  "fillStyle": "solid",
  "strokeWidth": 2
}
```

Use `strokeWidth: 2` as the default for all shape outlines (or whatever `theme.shapes.strokeWidth` says). Use `strokeWidth: 1` for lifelines, frame borders, and annotation lines (matches `theme.shapes.frameStrokeWidth`). Use `strokeWidth: 3` for the critical path arrow only.

### Hard constraints

**Architecture diagrams:** up to 4 accent colours when the diagram legitimately includes all four of UI/external, service, datastore, and queue/event kinds. For every other diagram type: 3 accents maximum. The goal is semantic clarity, not asceticism. Collapsing two distinct kinds into one colour to hit a count is worse than using one extra colour.

If your layout genuinely needs a fifth accent, reconsider whether the diagram scope is too broad. Code / evidence artifact elements (dark-slate background, green text) are exempt from this cap. They are content embedded in the diagram, not structural colour choices.

Stroke is always a darker shade than its paired fill. Never invert this. High contrast at the border keeps shapes legible when the diagram is exported at lower resolution or printed.

Do not add colour to arrows. Arrow colour encoding adds a second channel on top of line style, and the two conflict. Use line style (solid, dashed, dotted) to carry semantic meaning on arrows.

Background fill on the canvas itself should stay at the Excalidraw default white (#ffffff). Do not use a tinted canvas background. A tinted background shifts the apparent lightness of every fill colour on top of it and breaks the semantic colour map.

## Typography

Use Helvetica (`fontFamily: 2` in the Excalidraw JSON) for all technical diagrams. It renders cleanly at small sizes, and its neutrality keeps reader attention on content rather than style.

Use Virgil (`fontFamily: 1`) only when the diagram is intentionally hand-drawn or casual - a whiteboard sketch or a rough concept. Never mix font families within a single diagram.

Size hierarchy:

- Diagram title (top-level heading, standalone text block): 28-36px
- Section header or frame label: 24px
- Box label (service name, process name): 20px
- Body text or description inside a shape: 16px
- Annotation or note: 14px
- Fine print (version numbers, IDs, low-priority metadata): 12px

The minimum readable size is 14px. Use 12px only for content the reader can safely ignore - it should not carry information required to understand the diagram.

When a shape contains both a title and a description, the title is one size step larger than the description. A service box with a name label at 20px carries its description at 16px. Do not put a 16px title over a 16px description - the hierarchy collapses and the reader cannot find the primary label quickly.

## Arrow Semantics

Every arrow carries a specific meaning through its combination of line style and arrowhead. Treat these as a formal vocabulary.

Solid line with arrowhead: primary flow. Data moving forward through a pipeline, a synchronous request, a dependency from caller to callee. This is the default arrow type. If you are unsure which style to use, start here.

Dashed line with arrowhead: response, return value, or asynchronous message. A response travelling back along a request path, a callback, an event emitted after processing completes. Dashed returns pair with solid requests to show round-trip flows cleanly.

Dotted line with arrowhead: optional path. A feature-flag branch, a fallback route, a path that only executes under certain conditions. Use sparingly; too many dotted paths signals the diagram scope is too wide.

Solid line with no arrowhead: association. A relationship that has no direction, like a schema reference between two tables that reference each other equally.

Thick solid line with arrowhead: critical path. Reserved for the single most important flow - the happy path through a user journey, the data pipeline's main trunk. Use at most one critical path per diagram.

### Binding

Every arrow in the JSON must have both `startBinding` and `endBinding` set to the `id` of the source and target elements. An unbound arrow - one that visually points at a shape but has no programmatic binding - breaks diagram export, copy-paste, and downstream tooling. There are no exceptions to this rule.

### Labels

Every arrow carries a label unless the relationship is visually unambiguous from context. "Request" on an arrow between `Client` and `API Gateway` adds no information. "POST /orders" does. Default to specific; strip labels only when both the source and target names together make the relationship obvious.

Arrow labels must be bound to the arrow via `containerId` in the label element, not placed as separate floating text near the arrow midpoint.

## Arrow Crossings

Arrows must not cross. A crossing signals a layout problem. Restructure the graph before accepting a crossing.

Common restructuring techniques:

1. Flip a node to the other side of the diagram so its connections run parallel to existing arrows rather than across them.
2. Add a relay node (a small unlabelled circle or junction point) to bundle multiple arrows that share a path segment.
3. Split the diagram at a logical boundary and connect the two sub-diagrams with a frame reference.

If the domain genuinely has crossing dependencies (full-mesh service communication, for example), use a matrix or adjacency table instead of a directed graph.

## Shape Semantics

Rectangle: process, service, container, module. The default shape for anything that does work.

Rounded rectangle: UI element, button, card, user-facing component. The rounded corners signal "this is something a human touches."

Ellipse: start/end terminal in a flowchart, datastore in an architecture diagram. When used as a datastore shape, pair it with the purple colour from the semantic map above.

Diamond: decision point with two or more out-edges. When the decision label is longer than four words, use a labelled circle instead - a diamond with a long label produces an oversized shape that distorts the grid.

Frame (Excalidraw's frame element): swimlane, bounded context, or deployment boundary. Use a transparent background with a dashed stroke at 2px to avoid the frame visually dominating the content inside it.

## Label Placement

Arrow labels sit at the arrow's midpoint. Set a perpendicular clearance of 20px so the label text does not sit on the arrow line itself. In the JSON, this means the label element's `y` (or `x` for vertical arrows) is offset 20px from the arrow's midline.

When three or more arrows converge on one node, the labels for those arrows will collide at the node boundary unless you offset them. Place each label angularly around the node's centre: compute the angle each arrow makes with the node centre, then ensure adjacent labels are at least 25 degrees apart. If the angles are too close, shorten the label or move the arrow's endpoint 20-30px along the node's edge to create the angular separation.

## Roughness

Set `roughness: 0` for all technical diagrams. Excalidraw's default roughness introduces hand-drawn jitter that makes lines look imprecise. For technical work, precision signals correctness.

`roughness: 1` is appropriate for sketchy or exploratory diagrams where the hand-drawn feel signals "this is a draft."

`roughness: 2` is for whiteboard-style diagrams where the aesthetic is the point, not the precision.

Never mix roughness values within a single diagram. A shape at roughness 0 next to a shape at roughness 1 looks like a rendering error.

---

## Text in Shapes

Labels inside shapes must be bound via `containerId` in the text element's JSON, pointing to the shape's `id`. Do not place a separate floating text element visually on top of a shape and call it a label. Floating text breaks when the shape moves, when the diagram is exported, and when downstream tools parse the JSON.

Set `textAlign: "center"` and `verticalAlign: "middle"` on all in-shape labels. Left-aligned or top-aligned labels in shapes look accidental and make the diagram harder to scan.

When a label is too long to fit the shape at 16px, do one of three things in priority order: shorten the label text, increase the shape size to the next grid multiple, or reduce the font to 14px (the minimum). Never go below 14px and never let the label overflow the shape boundary.

Set `strokeColor: "#1e1e1e"` on the text element. In Excalidraw, `strokeColor` on a text element controls the INK colour, not a border. Setting it to `"transparent"` makes the label invisible. The rectangle's own border stroke is a separate property on the container.

## Presentation layer

Structural correctness gets the diagram legible. Presentation gets the argument across at arm's length. Every Create-lane architecture diagram should carry the three elements below. The graphviz layout script (`scripts/layout_architecture.py`) emits all of them from the semantic model.

### Diagram title

Every architecture diagram starts with a free-floating title at top-left at `(40, 30)`, `fontSize: 36`, `fontFamily: 2` (Helvetica), `strokeColor: "#1e1e1e"`. The title should state what the diagram *argues*, not the system name alone:

- "Multi-region HA banking: two active-active regions share a global ledger" (argues what the architecture does)
- "Banking platform" (displays what the system is, weak)

A subtitle sits at `(40, 80)`, `fontSize: 18`, `strokeColor: "#495057"`. Use it for scope, version, or the one-line context the reader needs: `"active-active / us-east / us-west / v4.2"`.

Without this title block, the reader has to piece the argument together from the nodes. With it, the diagram's claim is readable in the first second.

### Phase / column headers

For LR-direction diagrams with three or more sections (phases of a pipeline, stages of a request journey), add an uppercase header text above each section frame:

- `fontSize: 18`, `fontFamily: 2`
- `strokeColor: "#1e1e1e"`
- Horizontal position: same `x` as the section frame
- Vertical position: `section.y - 30` (sits just above the dashed frame)
- Text: section label in ALL CAPS (`SOURCES`, `EVENT BUS`, `STREAM + BATCH`, `STORES`, `SERVING`, `PRODUCTS`)

A reader should understand the pipeline phases without reading a single node label. The column headers are structure, the node labels are detail. Skip headers for TB diagrams. The vertical flow is already obvious from top-to-bottom reading order.

### Evidence artifacts

Technical diagrams must include at least one concrete specimen per major concept. Not every node needs one. Pick the three or four nodes whose real configuration is load-bearing for understanding the system:

- Kafka topic: `topic: orders.v2\npartitions: 16\nretention: 7d`
- LLM call: `model: llm-name\np99: 320ms\n~4k in / 800 out`
- API endpoint: `POST /auth/verify\n{jwt, scope, tenant}`

Format:
- Rectangle with `backgroundColor: "#1e293b"` (dark slate), `strokeColor: "#22c55e"` (green), `strokeWidth: 2`, `roughness: 0`.
- Bound text element with `fontFamily: 3` (monospace, the ONLY place monospace is correct), `strokeColor: "#22c55e"`, `fontSize: 14`.
- Positioned beside (usually right of) the node it annotates, with ~32px gap.
- The evidence rectangle is not a structural node. It does not count toward the 4-accent-colour cap, and it does not bind to any arrow.

A diagram with evidence artifacts reads like production documentation. Without them, even a structurally perfect diagram reads as conceptual. Fine for a pattern explainer, wrong for something an on-call engineer has to reason about at 3am.
